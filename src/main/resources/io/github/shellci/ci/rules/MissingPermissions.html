When neither the workflow nor the job declares permissions, the GITHUB_TOKEN receives the default permissions configured for the repository or organization. For many repositories, especially older ones, the default is read and write on every scope. The workflow's actual privileges then depend on a setting that is invisible in the code and can change at any time.

Ask Yourself Whether

  • The repository or organization default token permission is "Read and write".
  • The job runs third-party actions, installs dependencies or processes untrusted input.

There is a risk if you answered yes to any of those questions.

Recommended Secure Coding Practices

Declare a restrictive permissions block at the top of the workflow (for example contents: read) and widen it per job only where needed.

Sensitive Code Example

on: push
jobs:
  build:  # Sensitive
    runs-on: ubuntu-latest
    steps:
      - run: make

Compliant Solution

on: push
permissions:
  contents: read
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - run: make
