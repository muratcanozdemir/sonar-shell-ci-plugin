Pipelines often run code from elsewhere: GitHub actions and reusable workflows, GitLab include: files from other projects or URLs, and GitLab CI/CD components. Tags and branches such as @v4, @main or ref: main are mutable: the owner of the action, or anyone who compromises their account, can point them at new code. That code then runs in your workflow with your secrets and token. In March 2025 the compromise of tj-actions/changed-files retagged every release to a version that dumped CI secrets into public logs.

Ask Yourself Whether

  • The action is maintained by a third party you do not control.
  • The job has access to secrets, a write token, deployment credentials or publishes artifacts.

There is a risk if you answered yes to any of those questions.

Recommended Secure Coding Practices

  • Reference actions and reusable workflows by full-length commit SHA, with the version in a comment for readability.
  • In GitLab, set ref: of project includes and the @version of components to a full-length commit SHA. Do not use include: remote; mirror the file into a project you control and include it by commit.
  • Use Dependabot or Renovate to keep the pinned SHAs up to date.
  • Owners you fully trust (for example your own organization) can be listed in the trustedOwners parameter.

Sensitive Code Example

- uses: some-org/some-action@v2  # Sensitive

# GitLab CI
include:
  - remote: https://example.com/ci/build.yml        # Sensitive
  - project: other-group/ci-templates               # Sensitive: default branch
    file: /build.yml
  - component: $CI_SERVER_FQDN/acme/lint/check@main # Sensitive

Compliant Solution

- uses: some-org/some-action@8f4b7f84864484a7bf31766abe9204da3cbe65b3  # v2.1.0

include:
  - project: other-group/ci-templates
    ref: 3f2a7c9e1b4d5f6a7b8c9d0e1f2a3b4c5d6e7f80  # v2.3.0
    file: /build.yml
  - component: $CI_SERVER_FQDN/acme/lint/check@8c1f5e0d2b9a4c3e7f6d5b4a3c2e1f0d9b8a7c6e  # 1.4.0
