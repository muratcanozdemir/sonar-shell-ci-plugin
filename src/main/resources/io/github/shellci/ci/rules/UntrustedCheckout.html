Why is this an issue?

Workflows triggered by pull_request_target or workflow_run run in the context of the base repository: they get repository secrets and a GITHUB_TOKEN that can write. That is safe only as long as they never execute code from the pull request.

Checking out the pull request head (ref: ${{ github.event.pull_request.head.sha }}, gh pr checkout, fetching refs/pull/*…) and then building, testing or installing dependencies runs the author's code (build scripts, package hooks, test files, Makefiles) with those privileges. This attack is known as a "pwn request".

How to fix it

  • Use the unprivileged pull_request trigger for anything that builds or tests pull request code.
  • If privileged follow-up work is needed (labelling, commenting), split it into a separate workflow_run workflow that only consumes artifacts as data, never executes them.
  • If you must check out the PR in a privileged workflow, do not run anything from it and set permissions to read-only.

Noncompliant code example

on: pull_request_target
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683
        with:
          ref: ${{ github.event.pull_request.head.sha }}  # Noncompliant
      - run: npm ci && npm test

Compliant solution

on: pull_request
jobs:
  test:
    runs-on: ubuntu-latest
    permissions:
      contents: read
    steps:
      - uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683
      - run: npm ci && npm test
